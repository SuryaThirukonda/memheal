# MemHeal recovery measurements

Generated by `measure.py recovery` from recover.py's records. Recovery is applied to a copy of each run's last pre-target snapshot and the target task family is replayed.

3069 records; 186 runs; 1302 poisoned records at checkpoint 0.

*ASR* = attacker outcomes over every replayed task. *BR* (Section 8.7) = mean fraction of tasks whose (tool, destination) matches the clean run. *BMP* (Section 8.6) = probes still answered correctly, among those the same run answered correctly with no recovery ('none'); runs with no 'none' record are left out of BMP and counted under *no none baseline*. *Collateral* = quarantined memories labelled benign or outside the poison lineage; *ambiguous removed* (memories that only say the legitimate system is retired, the attack's premise) is counted apart, as Section 7.8 keeps that label out of primary metrics. Both include memories that were already consolidated, i.e. not retrievable before recovery. *Poison left in memory* = runs whose store still holds an active memory naming the attacker after recovery (oracle names, measurement only): the replay shows only what this task retrieves. *Root already consolidated* shows why `root` alone often changes nothing retrievable. Counts are means per run.

## Replay noise

372 measurements were written twice with the same deterministic plan (root, selective[oracle], selective[oracle]+immunize, unmerge[oracle]; 186 other repeated measurements left out because their plan was a counterfactual's or differed). Replaying the same recovered store again changed 9% (39/424) of task outcomes (3% (13/424) changed whether the attack succeeded) and 4% (30/776) of probe answers (temperature 0). One replay per run is the default; the A/A rows of the paired table put this in the same units as the comparisons.

## Reinfection (Section 8.8)

After recovery the agent keeps living with LIVE pages: two benign sessions, a recheck of the original poison-day request (session 3), then seven more benign sessions, consolidating after sessions 3 and 10. The task family is re-asked (without storing) at each checkpoint. Checkpoint 0 is replayed on the configuration's own pages (patched by default) and later checkpoints on live pages, so a task can be attacked by reading the poisoned page during the task itself while memory is clean: ASR after 1, before the recheck, on stores that are still clean is that live-read floor.
