Generated by `cost.py` from 514 runs (*_dense_direct_evolving, *_dense_composed_evolving, *_dense_procedural_evolving, *_dense_direct, *_dense_composed, *_dense_procedural), by memory mode: evolving, flat. Offline: no model call, no network.

- Storage (evolving, 274 runs): a run.db is 233,472 [212,992, 241,664] bytes over 50 [44, 55] memories (4,658 [4,475, 4,897] bytes per memory). Provenance tables take 44.8% [43.4%, 46.7%] of the file's pages (49.7% [48.4%, 51.5%] counting memory-row metadata), mostly fixed one-page-per-table overhead; of the stored payload they are 36.0% [34.3%, 37.6%]. Lineage is 0.59 [0.52, 0.85] edges and 36 [32, 53] payload bytes per memory (246 [223, 279] allocated). Per-session snapshot copies add 13.5 [13.0, 14.0] times the run.db.

## 2. Latency (offline, synthetic stores)

Machine: AMD Ryzen AI 7 PRO 350 w/ Radeon 860M, 16 cores, Python 3.11.16, SQLite 3.53.1, NumPy 2.4.6. Load average (1 / 5 / 15 min) 3.22 / 4.22 / 2.85 before the benchmark and 7.46 / 5.22 / 3.23 after it. Each cell: median / p95 over 30 timed calls after 3 warm-up calls, in milliseconds. Stores are sqlite files with the real schema, 384-d random unit float32 embeddings and 90-byte texts, written to a temp folder under results/cost and deleted afterwards; k = 5; the query embedder returns a constant vector, so the encoder is not in these numbers. Calls are interleaved: each round times every store size and part once, in a shuffled order, so load from elsewhere on the machine falls on every size alike rather than on one.

**Warning: the machine was busy** (a 1-minute load average above 4.0, a quarter of the cores). Other work competed with these timings, so they overstate the store's own cost and should be re-measured on an idle machine.
